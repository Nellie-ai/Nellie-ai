# Test plan

Ретроспективная структура от 03.11.2026. Существование такого плана до исторических проверок не заявляется.

## Основания и версии

| Источник | Использование | Ограничение |
| --- | --- | --- |
| ТЗ на MVP Telegram-бота v0.3, найденное в подключённом Drive | Публичные/приватные поля, подтверждение публикации, роли, одно назначение, жизненный цикл | Это требования, не доказательство реализации |
| Пользовательские сообщения о быстром UX и physical smoke, 23.09.2026 | Неполный и полный компактный ввод; дозаполнение; preview | [M01–M02](evidence/manual-records.md). Версия Telegram-клиента не записана |
| Сообщение автора о роли после тестирования, 23.09.2026 | Проверка смены координатора | [M03](evidence/manual-records.md). Полномочия отдельно проверялись агентом |
| Локальные audit/follow-up/master протоколы, 22.10.2026 | Проверки доступа и регрессия кандидатов | [Реестр](evidence/source-register.json). Снимки кода различаются; это не единая production-версия |

Исторический smoke parser предшествовал коммиту `ca9e218d475bfd760941630c1f141172e3044922`, согласно сообщению агента. До него было рабочее дерево поверх `97300b6`. Точный хеш dirty-состояния ручного прогона отсутствует. Начальная база октябрьского аудита указана как `4b7b90b13b32f612a6756ad485ed4cb65604c3e1` с локальными изменениями. SHA-256 проверенного финального кандидата указан в реестре. Эти идентификаторы не устанавливают версию на сервере.

## Цель и риски

Проверить, что координатор сохраняет введённые данные, получает корректный preview и не раскрывает приватные поля. Проверить границы доступа и устойчивость рабочего цикла на доступных свидетельствах.

| Риск | Проверяемое условие | Имеющееся свидетельство |
| --- | --- | --- |
| Потеря/неверное распределение полей при компактном вводе | Девять значений сохраняются; бот запрашивает отсутствующий полный адрес | Ручной FAIL и retest PASS, M01–M02 |
| Приватные данные в публичном представлении | Имя, телефон, полный адрес отсутствуют в preview | Ручной PASS для просмотренных образцов, M02 |
| Старая роль сохраняет полномочия | Изменение координатора сопровождается проверкой текущих прав | Наблюдение M03 и offline FAIL/PASS агента A01 |
| Список доступа попадает в группу | `/pending` доступен в private-контексте | Offline FAIL/PASS агента A01 |
| Устаревшая кнопка меняет новое назначение | Решение привязано к актуальному назначению/циклу | Offline FAIL/PASS агента A02 |

## Подтверждённый ручной scope

Быстрый ввод, пропущенный адрес, дозаполнение, полный ввод, публичный preview и наблюдение роли `/start`. Подробности и фактические результаты — в [manual-testing.md](manual-testing.md).

Проверка публикации в Telegram зафиксирована отдельным историческим инцидентом настройки: отсутствие бота в канале. Она не подтверждает успешный сквозной цикл. Ручные принятие двумя врачами, доставка private-данных победителю, финансы, отказы, возврат и полный отзыв доступа в доступных первичных свидетельствах не установлены: NOT RUN / evidence pending.

## Среда и данные

Исторический ручной smoke: Telegram, личный чат с ботом, тестовый аккаунт с временной ролью координатора. ОС/версия клиента и точная сборка для него не зафиксированы. Не переносить сюда версию Python из более позднего аудита.

Среда агента 22.10: Python 3.12.14, aiogram 3.31.0, SQLAlchemy 2.0.54; SQLite in-memory/временные синтетические БД, offline SQL и mocks. Реальный PostgreSQL и Telegram-доставка не проверялись этим набором.

В кейсе вместо данных участников используются метки `TEST_AREA`, `TEST_STREET`, `TEST_CLIENT`. Схема повторения дефекта содержит короткий синтетический phone-anchor с `+`: это часть исторической проблемы parser, не утверждение о корректной валидации телефонного номера. Контакты и адреса реальных клиентов не используются.

## Критерии оценки и завершения

- PASS: есть фактический результат конкретной проверки и указан исполнитель/среда.
- FAIL: наблюдение нарушает конкретное требование; исправление само по себе не меняет исходный FAIL.
- NOT RUN: нет доступного свидетельства выполнения в нужной среде. Это не утверждение, что никто никогда не запускал сценарий.
- Для признания исправления в production нужны версия, повторение исходных шагов и доказательства результата в согласованном тестовом контуре. Эти условия в данном кейсе не закрыты.

Разночтение финансового правила: Drive-ТЗ v0.3 описывает 50/50 для всех исполнителей; более поздняя задача от 23.09 задаёт координатору режим без распределения. Финансовый manual QA нельзя оценивать по одному старому документу. Утверждённая актуальная версия правила и ручной протокол — evidence pending.
